# Complexity Reduction (複雜度削減執行者)

簡單性不是做得少，而是**恰好做到需要的程度，不多也不少**。

複雜度是技術債的根源。過度設計浪費時間，且讓未來的修改更困難。

<HARD-GATE>
在 GREEN 步驟 (TDD)，不得：
- 添加超過讓測試通過所需的功能
- 重構「順手」看到的其他代碼
- 為「未來可能的需求」預先設計介面

只寫讓當前測試通過的最少量代碼。
</HARD-GATE>

## 三大原則

### YAGNI — You Aren't Gonna Need It
**不要構建你目前不需要的東西。**

觸發點：
- 「也許以後會用到...」
- 「如果需要擴展的話...」
- 「通用化一下比較好...」

以上想法出現時，刪除對應功能。等到真正需要時再加。

### DRY — Don't Repeat Yourself
**每一個知識點在系統中只應有一個唯一的、權威的表示。**

注意：
- DRY 是關於**知識的重複**，不是代碼的重複。
- 相似的代碼不一定是 DRY 違反。相同的**決策邏輯**重複才是。
- 過早抽象比重複代碼危害更大。

### 垂直切片 — Bite-Sized Tasks
**每次只做一件事，每件事 2-5 分鐘可完成。**

正確拆分示範：
- ✅ 「撰寫失敗測試」— 一個步驟
- ✅ 「執行確認失敗」— 一個步驟
- ✅ 「撰寫最小實作」— 一個步驟
- ✅ 「執行確認通過」— 一個步驟
- ✅ 「Commit」— 一個步驟

錯誤拆分示範：
- ❌ 「實作整個用戶認證模組」
- ❌ 「完成前端所有頁面」

## 複雜度偵測清單 (Self-Review)

在完成任何設計或實作後，對照以下問題：

**設計階段：**
- [ ] 我是否為「目前沒有需求」的功能設計了介面？→ 刪除
- [ ] 設計中是否有多個選項做同一件事？→ 選最簡單的
- [ ] 是否可以用 5 行代碼解決而我卻設計了一個模組？→ 直接寫 5 行

**實作階段：**
- [ ] 我加的代碼是否超過讓測試通過所需？→ 移除多餘部分
- [ ] 是否在 GREEN 步驟順手重構了其他東西？→ 還原，REFACTOR 再做
- [ ] 是否引入了新的依賴？→ 確認該依賴真的必要

**提交前：**
- [ ] 這個 commit 是否包含多個獨立的改動？→ 拆分 commit
- [ ] 文件/設計中是否有 TBD 或 TODO？→ 刪除或完成，不允許佔位符

## 過度設計的常見形式

| 模式 | 症狀 | 正確做法 |
|------|------|---------|
| 過早抽象 | 「先建一個抽象基類...」 | 直接實作，等第三次重複再抽象 |
| 配置驅動 | 「讓這個部分可配置，以後彈性...」 | 先寫死，等真正需要配置時再提取 |
| 框架思維 | 「這部分應該做成可插拔的...」 | 做最直接的實作 |
| 防禦性預留 | 「以後可能會支援多語系，所以...」 | YAGNI。等有需求再加。 |
| 大爆炸重構 | 「趁機把整個模組重構一下...」 | 只改需要改的，不影響本次需求的代碼不動 |

## 與其他 Skills 的整合

- **tdd-enforcer**：GREEN 步驟嚴格遵守此 skill 的最小實作原則
- **grill-requirements**：設計階段主動使用 YAGNI 剪枝，移除所有不必要功能
- **writing-plans**：計畫中每個任務粒度必須符合垂直切片（2-5 分鐘）
- **verification-before-completion**：完成前以此 skill 的清單做最終複雜度審查
