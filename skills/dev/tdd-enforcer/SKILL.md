# TDD Enforcer (測試驅動開發執行者)

此技能用於對抗 Vibe Coding，確保專案中的核心邏輯具備極高的可靠性與可測試性。
當用戶要求新增功能或修改核心邏輯時，你必須嚴格遵守以下 Red-Green-Refactor 工作流，**禁止直接給出實作代碼**。

<HARD-GATE>
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST.

如果你在沒有失敗測試的情況下已經寫了代碼：
- 不要保留它作為「參考」
- 不要「邊寫測試邊調整」它
- 不要看它
- **刪除它。重新開始。**

沒有例外。
</HARD-GATE>

## 核心原則
**如果你沒有親眼看著測試失敗，你就不知道它是否在測試正確的東西。**

違反這條規則的字面意義，就是違反了這條規則的精神。

## 執行步驟 (The TDD Loop)

### 1. 🔴 RED — 撰寫並驗證失敗的測試 (MANDATORY)

- **行動**：根據需求，首先撰寫一個或多個測試案例 (Test Cases)。
- **規則**：
  - 測試必須精準描述**預期行為**，而非實作細節。
  - 必須實際**執行測試並確認它失敗**（不是錯誤，是失敗）。
  - 確認失敗訊息符合預期（因為功能缺失而失敗，而非因為語法錯誤）。
- **驗證確認**：
  - ✅ 測試失敗（不是 error）
  - ✅ 失敗訊息符合預期
  - ✅ 確認是因為功能缺失而失敗，而非 typo
- **如果測試直接通過**：你在測試已有行為。修正測試，重新執行直到看見紅燈。

### 2. 🟢 GREEN — 撰寫剛好能通過的實作 (MANDATORY)

- **行動**：一旦確認測試失敗，撰寫**最少、最簡單**的代碼來讓測試通過。
- **規則**：
  - 不要做任何過度設計 (No over-engineering)。
  - 不要預測未來的需求（遵循 YAGNI 原則）。
  - 代碼唯一的功能就是讓剛剛的紅燈變綠燈。
  - **不要在 GREEN 階段重構其他代碼。**
- **驗證確認**：
  - ✅ 測試通過
  - ✅ 其他既有測試仍然通過（無回歸）
  - ✅ Console 輸出潔淨（無 error、無 warning）

### 3. 🔵 REFACTOR — 重構與優化

- **行動**：在測試全數通過的安全網下，優化代碼結構。
- **規則**：
  - 清理壞味道 (Code smells)。
  - 提升代碼的自我表達力 (Readable)。
  - 確保優化後，**所有測試依然保持綠燈**。
- **輸出**：展示重構後的乾淨代碼，並再次執行測試確認。

## 完成前驗證清單 (Pre-Completion Checklist)

在宣告任何功能完成前，必須逐項確認：

- [ ] 每個新函式/方法都有對應測試
- [ ] 親眼看著每個測試失敗後才實作
- [ ] 每個測試的失敗原因符合預期（功能缺失，不是 typo）
- [ ] 撰寫了最少量的代碼讓測試通過
- [ ] 所有測試通過
- [ ] Console 輸出潔淨（無 error、無 warning）
- [ ] 測試使用真實代碼（只在不可避免時才用 mock）
- [ ] 邊界情況與錯誤路徑已覆蓋

無法勾選所有項目？代表你跳過了 TDD。重新開始。

## 常見藉口與反駁

| 藉口 | 現實 |
|------|------|
| 「太簡單了不用測試」 | 簡單的代碼也會壞掉。測試只需要 30 秒。 |
| 「我會在完成後補測試」 | 事後補的測試直接通過，什麼也證明不了。 |
| 「我已經手動測試過了」 | 手動測試 ≠ 系統化測試。沒有紀錄，無法重跑。 |
| 「TDD 會讓我變慢」 | TDD 比事後除錯快。 |
| 「刪掉 X 小時的代碼太浪費」 | 沉沒成本謬誤。保留未驗證的代碼是技術債。 |

## ⚠️ 絕對禁忌
- **禁止跳步**：如果沒有失敗的測試，絕對不准開始寫業務代碼。
- **禁止大包裝**：不要一次寫完所有測試與實作，將功能拆解為「垂直切片 (Vertical Slices)」，每一個小切片跑一次 TDD 循環。
- **禁止事後補測試**：測試必須在實作之前撰寫，且必須先失敗。
